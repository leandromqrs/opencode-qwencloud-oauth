# QwenCloud protocol provenance

Baseline: installed `@qwencloud/qwencloud-cli` **1.5.0**, official repository [QwenCloud/qwencloud-cli](https://github.com/QwenCloud/qwencloud-cli), inspected revision `264999e87d2fe819a9c570a9f3cbc1c9864a5163`.

The installed package manifest confirms its identity and repository; bundled constants corroborate the inspected protocol. This is not a claim of byte-identical build provenance. Source research did not read CLI credential files or invoke inference.

## Device authorization

Official sources:

- [Auth client](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/api/auth-client.ts)

- [Client identity](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/auth/client-id.ts)
- [PKCE](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/auth/pkce.ts)

Initialization is `POST https://t.qwencloud.com/cli/device/code` with query parameters `client_id`, `code_challenge` and `code_challenge_method=S256`. The client ID is a locally generated persistent UUID, not the public client identifier from Qwen Code subscription OAuth. The plugin must own its own client ID.

The response uses `Success` and `Data`, whose fields include `Token`, `VerificationUrl`, `ExpiresIn` and `Interval`. Polling is `POST /cli/device/token` with `client_id`, `token` and `code_verifier`. Successful credentials include `Data.Credentials.AccessToken` and `ExpireTime`. The CLI also accepts compatibility spellings.

These query values are secrets: never copy the upstream pattern of exposing complete URLs in errors. Two public device initializations verified the production browser destination as `https://account.qwencloud.com/sso/OIDCAuth`, with query keys `app_type`, `lang`, `auth_token` and `oauth_callback`. The nested callback destination is `https://www.qwencloud.com/oauth/confirm`, with its own `auth_token`. Validation pins these destinations and rejects duplicate or extra parameters; the server URL is returned unchanged. No issued codes, tokens or complete URLs were logged or retained, and no token polling or account approval was performed in those checks.

The inspected CLI has no implemented refresh endpoint. Expired management credentials require login again. Its displayed scopes are hardcoded status metadata, not negotiated evidence.

## Management requests and catalog

The authenticated gateway is `POST https://cli.qwencloud.com/data/v2/api.json` with Bearer management credentials. Its envelope contains `product`, `action`, `region` and `params`; parameter values are flattened to strings. HTTP 200 alone is insufficient: the outer business `code` must be the string `"200"`.

Model discovery uses `product: AliyunDeliveryService`, `action: ListModelSeries`, `region: ap-southeast-1` and `params.Language: en-US`. Groups are returned under `data.Data`, containing `Items`. IDs and metadata use the actual `Model`, `InferenceMetadata` and `ModelInfo` fields. Do not reuse the old service's embedded reasoning mappings.

Sources: [request adapter](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/api/request-adapter.ts), [models service](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/services/models-service.ts).

## Inference is a separate credential boundary

The [invocation resolver](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/services/invocation-credential-resolver.ts) obtains API keys separately from management OAuth. Model calls use the compatible Chat endpoint, not the control-plane gateway.

The inspected CLI uses `https://token-plan.ap-southeast-1.maas.aliyuncs.com/compatible-mode/v1` for Token Plan. The plugin now uses the current documented endpoint `https://token-plan.maas.qwencloudapi.com/compatible-mode/v1`, as described in [Token Plan discovery and endpoint provenance](token-plan.md). The old endpoint was also Token Plan, not PAYG; its continued compatibility has not been disproved. Token Plan keys use the `sk-sp-` prefix. Although the isolated transport utility knows the CLI's DashScope Intl destination, the registered driver accepts Token Plan keys only: it never falls back to PAYG or sends management tokens to model endpoints.

Native OAuth completion and authenticated catalog discovery were verified on 2026-11-06: the account returned 186 catalog entries. Catalog visibility does not establish model entitlement. Token Plan reads selected the seat route but returned an unrecognized summary shape; no balance or absence of subscription has been established.

The native driver provides an operation-scoped `FetchHttpClient.Fetch` implementation. It applies `prepareRequest` after host HTTP-hook serialization and immediately before fetch, so redirect refusal and cancellation are not lost in that conversion. A scope-owned deadline and explicit response-reader cancellation keep streaming timeouts effective through garbage collection. Tests exercise the host conversion sequence, real loopback sockets and compiled provider loading with separate Effect copies. No host binary patch, global fetch replacement or unsafe bypass is required.

On 2026-11-06, the user supplied a separate key through a private secret prompt; it was stored through OpenCode's native key connection, not in project files. Two minimal native chat checks reached the provider: `qwen3.6-plus` was denied as unpurchased, and `qwen3.7-plus` returned exhausted monthly quota with reset on November 14 at 16:00 UTC. These are live provider errors, not successful model generations. No automatic purchase, quota retry or alternate-plan fallback was attempted.

## Explicit inference key flow

The inspected CLI's login does not create inference keys. Missing keys direct users to the console's API Keys page. Public console assets expose separate operations for PAYG, personal Token Plan and team Token Plan key creation, but their shared browser transport uses session cookies and CSRF handling. That does not establish that a CLI Bearer management token can invoke those actions through the CLI gateway.

The integration follows the CLI rather than those browser-only operations: users create a key at `https://home.qwencloud.com/api-keys` and supply it separately. No account key was created, reset, revealed or revoked. Automatic provisioning and experimental console key probes are not part of this flow.

## Token Plan quota flow

The CLI's `usage summary` delegates to [TokenPlanService](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/services/tokenplan-service.ts). It calls BSS `QuerySubscriptionGray`, then uses the seat summary and addons for migrated accounts, or `DescribeFrInstances` for legacy team, personal and addon commodities. The personal legacy commodity is `sfm_tokenplanpersonal_dp_intl`.

The console's personal `/tokenplan/personal/api/v2/usage` gateway route is not used by the inspected CLI. Experimental probes returned an empty `ret` tuple, not a recognized success. They established neither a quota nor OAuth permission for personal console operations, and are excluded from the CLI-aligned flow. Failed or unrecognized BSS responses remain inconclusive instead of being converted to zero balance or no subscription.

No evidence established that supplying the inference key to BSS fixes missing quota. The CLI's [`ensureAuthenticated`](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/auth/credentials.ts#L371-L388) rejects expired sessions and documents that there is no refresh mechanism.

After user reauthentication, the coordinating session reported a native quota response with no balances and `GetSeatSubscriptionSummary: invalid-response`; management status was `configured-unverified`. This confirms the explicit read reached the upstream parser, not that an allowance is absent. The additional team-aggregate experiment was removed; a team total cannot establish the current user's Individual allocation.

User-authorized native RPC observations on 2026-11-11 returned `quota.state: disconnected` while `status.connected` was true and the separate inference key was stored. The old quota branch collapsed expired, unavailable and switched-account credentials into disconnected, so those outputs alone cannot prove which branch occurred. The correction reports those branches distinctly and learns management auth state only on explicit reads. No fresh balance, expiration timestamp or successful reauthentication was established by that observation; the earlier empty seat summary remains unresolved.

A subsequent user-authorized location reload returned `credentials-unavailable`, not a balance. Reviewing the exact [OpenCode 2.2.5 resolver](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/core/src/integration.ts#L743-L773) established a local integration bug: when a refresh callback is registered, native resolution invokes it for any OAuth credential expiring within five minutes, before returning the bare credential value. This plugin had registered a callback that only throws `requireReauthentication`, so native resolution could fail even while the access token was still valid; the discovery catch then erased the cause. The callback is now omitted, as permitted by the SDK's optional refresh contract. Synthetic host-contract tests verify that near-expiry credentials reach BSS and actually expired credentials return `session-expired` without upstream requests. This finding establishes the code defect, not the live credential's exact expiration or a numeric allowance.

The same follow-up showed `status.management: stored-unverified` immediately after the quota error. A separate observation-reset defect was reproducible: discovery cleared management observations on every `integration.updated` broadcast. The [host's integration registry](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/core/src/integration.ts#L379-L385) and [runtime connection status updates](https://github.com/anomalyco/opencode/blob/v2.2.5/packages/core/src/integration.ts#L829-L835) publish this event without identifying a changed credential. Discovery no longer treats it as credential replacement, and ignores `credential.switched` events for unrelated integrations. Global `credential.updated` events still clear observations conservatively because their payload does not identify a credential.

## Post-reboot inference and host separation (2026-11-12)

The reported `Connection lost while reading the response` failure was traced to the plugin's own `TimeoutError`, not an inference-key rejection. Sanitized stored message timings showed 64,991 milliseconds before reasoning and 55,055 milliseconds of reasoning, for a total request lifetime of 120,049 milliseconds on `qwencloud/qwen3.8-max`. The displayed reasoning duration alone therefore understated the time covered by the 120-second request deadline.

The default deadline was raised to 600,000 milliseconds, retaining explicit overrides and manual cancellation. After explicit user approval, the existing global QwenCloud option was also changed from 120,000 to 600,000; changing only the default would not have affected that configuration. The full suite passed 111 tests, typecheck and build. Following an authorized reload, one authorized native generation returned `OK` in 3.917 seconds, with the runtime timeout verified as 600,000 milliseconds. A synthetic streamed response lasting beyond two minutes guards against the old default. The short live call establishes successful inference, not a ten-minute live endurance test.

Quota diagnostics exposed a separate process boundary. The OpenChamber host owned the loopback listener and returned `40.87152760914666` percent remaining, while a different CLI service process reported a failed bridge lease. A targeted Custom-provider refresh in that CLI service returned no QwenCloud row and an aggregate network error. That aggregate error alone does not establish a particular authentication failure. Source inspection established that the original registry and temporary key were process-local and could not coordinate independent hosts using the same fixed port. The user explicitly approved replacing that limitation with a persistent, private, bridge-only key and automatic cross-process coordination; OAuth and inference credentials remain separate.

Shared mode was subsequently implemented and enabled in configuration with `shared: true`, retaining port 62367 and the existing Custom-provider definition. Synthetic two-process tests cover concurrent attachment, authenticated discovery, owner-exit takeover and cross-process executable fencing. Review identified an interrupted hard-link publication that could strand valid key/root records; deterministic regressions now cover recovery through validated matching private staging inodes while arbitrary hard links still fail closed. The reconciled suite passed 123 tests, typecheck, build and diff checking. Runtime migration still requires a user-controlled restart of all old hosts: an existing ephemeral-key listener must not be adopted without proof or terminated by the plugin. These checks establish implementation readiness, not a completed post-restart live quota validation.
