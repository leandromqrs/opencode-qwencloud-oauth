# Token Plan discovery and endpoint provenance

## Endpoint

The official [Individual quick start](https://docs.qwencloud.com/token-plan/personal/token-plan-personal-quickstart), [Team quick start](https://docs.qwencloud.com/token-plan/team/token-plan-team-quickstart) and [regions reference](https://docs.qwencloud.com/developer-guides/getting-started/regions) explicitly document the OpenAI-compatible base URL `https://token-plan.maas.qwencloudapi.com/compatible-mode/v1`. The driver pins that base and POST `/chat/completions`, with redirect refusal and no automatic PAYG fallback. A separate native Token Plan key is still required; management OAuth is never an inference key.

The previous `token-plan.ap-southeast-1.maas.aliyuncs.com` host was also a Token Plan endpoint. The migration follows current documentation and the support response provided by the user; it does not claim the old host is broken, that a key needs replacement, or that the new host has been verified by a live request during implementation.

## Why the general catalog is insufficient

The plugin follows the pinned official CLI's [`ListModelSeries` request](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/services/models-service.ts#L190-L200) at the CLI management gateway. The CLI's [`flattenApiModels`](https://github.com/QwenCloud/qwencloud-cli/blob/264999e87d2fe819a9c570a9f3cbc1c9864a5163/src/api/model-mapper/model.ts#L117-L122) traverses the same `Data[].Items[]` groups as this plugin. There is no version filter or local pagination truncating that parser.

An authorized refresh on 2026-11-12 at 22:06 UTC returned 186 models without `qwen4-max-preview`, `qwen4.0-max-preview` or `auto`. That observation does not reveal pagination fields: the existing RPC exposes only sanitized metadata, not the original envelope. It also does not establish that `ListModelSeries` is exclusively PAYG or explain the backend's omission.

The official [pricing page](https://www.qwencloud.com/pricing/token-plan) loads the public [Token Plan table component, version 0.0.2](https://q.alcasset.com/npm/@ali/hmod-qwencloud-token-plan-model-list-table/0.0.2/index.js). That component uses `zeldaHttp.dashscopeModel./zelda/api/v1/modelCenter/listTokenPlanModels`, with `input: { pageNo: 1, pageSize: 100, edition: "PERSONAL" }`, rather than `ListModelSeries`. It maps `data.list` items using `modelId`, `provider` and `capabilities`. The Singapore browser transport uses `ap-southeast-1-cs-data.qwencloud.com/data/api.json`, product `sfm_bailian` and action `IntlBroadScopeAspnGateway`, with session cookies and a `sec_token`. Public source establishes a different catalog contract, not compatibility with the CLI OAuth credential. The plugin does not scrape that page, import browser cookies, probe that console API, or introduce a new authentication flow.

## Explicit documentation supplement

Until a supported Token Plan discovery integration is established, the approved local correction uses a deliberately small audited snapshot from the official [Individual supported-model table](https://docs.qwencloud.com/token-plan/personal/token-plan-personal-overview) and [Team supported-model table](https://docs.qwencloud.com/token-plan/team/token-plan-team-overview), reviewed on 2026-11-12. Both list `qwen4-max-preview` and `auto`. Qwen4 preview is Token Plan only, not PAYG. The documentation and the support response supplied by the user identify `qwen4.0-max-preview` as an alias; the native inventory publishes only the canonical name, normalizing an observed alias without duplicating the selector entry. An alias does not become a separate allowed request ID.

The supplement is not a live API result or account entitlement check. Supplemental RPC entries have `metadata: "token-plan-documentation"` and explicit `provenance` containing source URLs, review date and validity bounds. The RPC's separate `tokenPlanSupport` field identifies this policy. `accountListed` and durable snapshots retain only sanitized management observations. No documentation entry is persisted as a model observed for an account. Existing management models, prices and order are retained, except canonicalizing the known alias and applying the documented preview expiration. Documentation-only entries have unknown limits, modalities, tools and tariffs; they do not borrow another model's prices or limits. Qwen4 effort variants are separately grounded in the API reference below. Existing catalog-based pricing behavior is unchanged.

Publication requires an active management connection with a successfully stored, nonempty account-bound catalog. A new connection, missing or invalid cache, failed initial refresh, account switch or authorization-denial tombstone cannot publish the supplement. Existing inference-key source fencing, connection checks and the HTTP-hook membership guard apply to supplemented models as well. Neither the management account, an advertised model nor the key format proves that the inference key belongs to that account or can execute that model. Existing general-catalog visibility is preserved rather than silently restricting all models to a static subscription list.

The official preview runs from **2026-11-11 10:00 UTC+8 through the end of 2026-11-25 UTC+8**. The implementation uses the exclusive end **2026-11-26 00:00 UTC+8**. Both supplements are bounded to that window; applying the same review deadline to `auto` is a conservative snapshot policy, not a claim that `auto` retires then. Qwen4 canonical and alias entries are excluded outside the preview window even if an old management snapshot contains them. An `auto` model independently returned by management remains a management observation after the supplemental snapshot expires.

The projection is recomputed on cache restoration and the existing periodic discovery synchronization. The HTTP guard recomputes current bindings, so a preview cannot be dispatched after expiration while a selector update is pending. No new timer, upstream background request or startup documentation fetch is introduced. The `auto` model's documented unsupported `tool_choice` and `thinking_budget` fields are rejected at final request validation; no payload fields are silently removed.

## Qwen thinking effort

The official [Chat Completions reference](https://docs.qwencloud.com/api-reference/chat/openai-chat) and [thinking guide](https://docs.qwencloud.com/developer-guides/text-generation/thinking), reviewed on 2026-11-12, document `low`, `medium` and `xhigh` reasoning effort for exactly `qwen4-max-preview`, `qwen3.8-max`, `qwen3.8-max-0902`, `qwen3.8-flash`, `qwen3.8-2.4t-a95b` and `qwen3.8-27b`. The documented Qwen4 alias receives the same controls before existing canonicalization. Native OpenCode variants expose these levels and `none`, the documented compatibility value that disables thinking. `high` and `max` map upstream to `xhigh`; they are not separate intensity levels. No effort variants are inferred for `auto`, other model families or unlisted Qwen IDs.

OpenCode 2.2.5 variants use `settings.reasoningEffort`, which the existing OpenAI-compatible driver serializes as top-level `reasoning_effort`. Selecting no variant leaves the parameter absent: upstream then defaults to effort `xhigh` with thinking budget 131072. Explicitly selecting `xhigh` maps upstream to budget 262144; `low` maps to 4096 and `medium` to 16384. The plugin sends the level, not an invented token budget, and does not overwrite the unselected default. More thinking can consume more tokens and affect Credits usage; these controls do not establish a fixed charge or an inference entitlement.

Thinking enablement, thinking-token budget and discrete effort are distinct controls. Advanced raw body overlays can set `enable_thinking` or `thinking_budget`; arbitrary settings of those names are not translated by this driver. Do not combine a `thinking_budget` body overlay with an effort variant: the documented API rejects requests containing both `thinking_budget` and `reasoning_effort`. The plugin does not silently remove either field or add a separate budget selector. The native effort list is derived again from sanitized IDs during catalog restoration, not saved as an account observation. Preview expiration and account fences remain unchanged.

## Activation and cache migration

The endpoint is part of the existing routing fingerprint and account cache key. Changing it makes old-host snapshots and denial records ineligible for restoration under the new route; the plugin does not rewrite or migrate them out of band. A fresh explicit successful catalog refresh is required before models can appear under the new routing fingerprint. Failed discovery cannot be bypassed by the documentation snapshot. The new route does not inherit old cached observations; a denial on the new route retains the existing durable tombstone behavior.

Implementation and synthetic tests do not activate the plugin. Loading the changed build, refreshing authenticated metadata and checking a live generation remain separately authorized actions. No inference, key replacement, purchase, global configuration change or reload is part of this local correction.

## Authorized activation evidence

After independent review, all 144 tests passed without skips, followed by typecheck, build and whitespace checks. The user then separately authorized a host reload and one authenticated catalog refresh on 2026-11-12. Local status confirmed a fresh stored catalog and 188 supported entries. Native inventory confirmed `Qwen4 Max Preview` and `auto` on the documented endpoint; Qwen3.8 Max retained its existing prices. The refresh command returned truncated JSON to its caller, so completion was verified through subsequent local status and inventory reads, without repeating the upstream refresh.

The supplemental models still have unknown native limits and prices. Presence in inventory verifies publication, not successful generation or account entitlement. No inference, key replacement, purchase, commit or push was performed during activation.
